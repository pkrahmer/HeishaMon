# The shadow sketch, its host twin and the bridge

## Description

The loop of the story before runs the whole control path. This story puts it on the owner's spare D1 mini, live, fed from the house:

- **The shadow protocol**, a small module beside the loop. It handles framed request lines (configure, start, input, stats) and produces a framed record line after each decision. The sketch and the host twin only move lines and read their clock.
- **The shadow sketch**, `tests/control/device/shadow/shadow.ino`. It runs the protocol on the D1 at 230,400 baud with the board's own clock, widened by `ctl_clock`.
- **The host twin**, `tests/control/device/shadow_host.c`. It runs the same protocol over standard input and output, with the host's monotonic clock and an optional speed factor, so that a test covers minutes of loop time in seconds.
- **The bridge**, `tests/control/device/shadow.py`, on the PC:
  - it reads a configuration file, configures and starts the board or the twin, and subscribes read-only to the owner's MQTT broker;
  - it forwards each message as an input line;
  - it writes every record and every input to CSV files with the wall time.
  
  With `--replay` it reads a capture file instead of the broker, which is how its test runs.
- **A test**, `tests/control/device/test_shadow.py`, that `make test` runs.

Nothing in the shadow can reach the pump: the board is not wired to it, the router's commands are only written into the records, and the bridge only subscribes. The loop runs with `assume_landed` true.

```c
/* ctl_shadow.h */
#define CTL_SHADOW_LINE_MAX 240 /* the longest request line, without frame and line end */

typedef struct {
    ctl_loop_config config;
    ctl_loop loop;
    bool started;
    uint32_t inputs;
    uint32_t records;
    bool has_record;   /* a record waits to be taken by ctl_shadow_poll */
    ctl_loop_record record;
} ctl_shadow;

void ctl_shadow_init(ctl_shadow *shadow);
void ctl_shadow_handle(ctl_shadow *shadow, const char *line, double now, char *reply, size_t size);
bool ctl_shadow_poll(ctl_shadow *shadow, double now, char *text, size_t size);
```

The shadow protocol. Lines and replies carry the frame of `ctl_frame` on the line, as in the replay. The functions here work on the text inside the frame.

`ctl_shadow_init` sets `ctl_loop_config_defaults` for 4 rooms with `assume_landed` true, not started, and both counts 0.

| Request | Effect | Reply |
|---|---|---|
| `K rooms <n>` | the room count, 1 to 16; every weight back to 1.0 | `ok` |
| `K weight <i> <w>` | the weight of room `i` | `ok` |
| `K room_timeout_s <s>` | the room timeout | `ok` |
| `K solar_gain_factor <g>` | the core's `solar_gain_factor` | `ok` |
| `K cooling <0 or 1>` | 1 adds `COOLING` to `allowed`, 0 removes it | `ok` |
| `G` | `ctl_loop_config_valid`; when valid, `ctl_loop_init` at `now` and started | `ok`, or `bad` and not started |
| `I <input> <room> <payload>` | `ctl_loop_input`; `<input>` is `room`, `outdoor`, `heat`, `valve`, `defrost` or `pv`; `<room>` decimal; `<payload>` everything after the third space | `taken`, `no_reading`, `refused` or `bad` |
| `S` | | `stats inputs=<n> records=<n>` |

- Every number in a `K` line is parsed by `ctl_payload_parse` as a bare number. A count or an index must be a whole number.
- A `K` line after `G` gives `error`.
- An `I` line before `G` gives `error`.
- `inputs` counts every `I` line that got one of the four input replies.
- Any other line gives `error`: an unknown request or name, a missing field, a field that does not parse, a value outside its range, and a line longer than `CTL_SHADOW_LINE_MAX`.

`ctl_shadow_poll`:

- When started, it calls `ctl_loop_tick` at `now`.
- When the tick returns a record, it counts it and writes `D ` followed by the record's text from `ctl_loop_format_record`, and returns true.
- Otherwise it returns false and writes nothing.

The sketch:

- It prints a framed `ready`, then answers each framed line with one framed reply.
- A line whose frame does not check gets a framed `error`.
- It calls `ctl_shadow_poll` on every pass of `loop()` with the widened `millis()` in seconds. It writes each record framed, with ` heap=<free heap>` appended to the record text before the frame.
- It answers `S` with the protocol's stats line followed by ` heap=<n> uptime_s=<n>`.

The host twin:

- It behaves as the sketch over standard input and output, with `heap=0`.
- Its clock is the host's monotonic clock since its start, multiplied by `--speed <factor>` (a positive number, default 1).
- It polls at least every 10 ms of wall time, also while no line arrives.
- It ends with exit status 0 at the end of its input.
- A wrong argument prints `usage: shadow_host [--speed <factor>]` to standard error and exits with 2.

The bridge `shadow.py`. It uses the standard library, and `paho.mqtt` only without `--replay`, and `serial` only with `--port`.

- **Arguments.** `shadow.py --config <file> (--port <port> | --command <command>) --out <folder> [--minutes <m>] [--replay <capture>]`.
  - `--command` is split by `shlex.split`.
  - Without `--minutes` it runs until interrupted.
  - A wrong command line or configuration exits with 2.
- **Configuration** (JSON):
  - `broker` with `host` and `port`;
  - `rooms`, a list of `topic` and `weight`;
  - `outdoor`, `heat` and `valve`, each a topic;
  - `defrost` and `pv`, each a topic or `null`;
  - `room_timeout_s`, `solar_gain_factor` and `cooling` (true or false).
  
  The example file holds placeholders only: no real host and no real device address.
- **Start.** It opens the link: with `--port`, the reset pulse and the wait for `ready` as in the replay. It sends the `K` lines for the rooms, their weights, the timeout, the gain and cooling, then `G`, and stops with exit 1 when a reply is not `ok`.
- **Forwarding.** It subscribes to every configured topic. Each message whose payload is ASCII becomes `I <input> <room> <payload>`, with line ends removed, and is sent framed.
  - A message that is not ASCII, or whose line would exceed `CTL_SHADOW_LINE_MAX`, is not sent. It counts as skipped.
  - Retained messages are forwarded like any other.
- **Output**, in the folder `--out`, all three files appended to:
  - `decisions.csv`: one row per `D` line. The first column is the wall time in ISO 8601 UTC, then one column per key of the line in its order.
  - `inputs.csv`: one row per message, with the wall time, the input, the room, the topic, the payload, whether it was retained, and the reply. Replies are matched to the inputs in order.
  - `errors.log`: one line per broken frame or unexpected reply, printed safely as in the replay.
- **Summary.** At the end it prints `shadow: <records> records, <inputs> inputs (<taken> taken, <no_reading> no reading, <refused> refused, <bad> bad), <skipped> skipped, <broken> broken lines`. It exits with 0.
- **Capture.** With `--replay`, each line of the capture is a JSON object with `after_s`, `topic`, `payload` and `retain`. It is delivered at that many wall seconds after the start, instead of from the broker.

## Acceptance criteria

1. The `K` lines, as rows of one table test on a fresh shadow:
   - `K rooms 3` gives `ok` and a count of 3 with weights 1.0;
   - `K weight 2 2.5` gives `ok`;
   - `K weight 3 1` after `K rooms 3` gives `error`;
   - `K rooms 0`, `K rooms 17` and `K rooms 2.5` give `error`;
   - `K room_timeout_s 10800` gives `ok`;
   - `K solar_gain_factor 0.02` gives `ok`;
   - `K cooling 1` adds the cooling bit, and `K cooling 0` removes it;
   - `K cooling 2` and `K nothing 1` give `error`.
2. Start and order:
   - an `I` line before `G` gives `error`;
   - `G` with the defaults gives `ok`;
   - a `K` line after it gives `error`;
   - `G` after `K room_timeout_s 0` gives `bad`.
3. The `I` lines, as rows of one table test after `G`:
   - `I room 0 {"ts":1,"v":21.0}` gives `taken`;
   - `I room 9 21.0` gives `bad` with 4 rooms;
   - `I outdoor 0 5` gives `taken`;
   - `I outdoor 0 99` gives `refused`;
   - `I valve 0 0` gives `no_reading`;
   - `I heat 0 3200` gives `taken`;
   - `I fan 0 1` gives `error`;
   - `I room x 1` gives `error`;
   - a line of `CTL_SHADOW_LINE_MAX + 1` characters gives `error`.
   
   `S` then reports the number of input replies.
4. The records: after `G` at 0.0, `ctl_shadow_poll` at 59.0 returns false, and at 60.0 true with a text that starts `D t=60.0 demand=NO_DEMAND reason=WAITING_FOR_INPUTS`. The next record comes at 120.0.
5. The host twin: piped a framed `G`, it prints the framed `ready` and `ok`; with `--speed 60` and the input kept open for 2.5 s, it prints at least 2 framed `D` lines. With `--speed 0` it prints the usage line and exits with 2.
6. The bridge against the twin, run by `test_shadow.py` through `make test`:
   - `shadow.py --command "<twin> --speed 120" --replay tests/control/device/data/shadow_capture.jsonl --minutes 0.1` writes at least 10 rows to `decisions.csv`. Its capture holds four rooms, outdoor, heat and valve within the first second, and one message on an unconfigured topic;
   - some row has the reason `SEEDED`;
   - every row after the seeding has `rooms=4:4.0/4.0`;
   - `inputs.csv` has a row per configured message with the reply `taken` or `no_reading`;
   - the summary line reports 0 broken lines;
   - the run takes less than 15 s.
7. The bridge refuses a wrong start: a configuration without `rooms` exits with 2, and so does a call with both `--port` and `--command`.
8. `replay.py` works as before: `make test` still prints its summary line with 0 mismatches.
9. `make device` compiles both sketches and prints their memory lines.
10. `make check` stays green.
11. docs: `docs/control/shadow.md` is new. It says:
    - what the shadow is, and that nothing can reach the pump (three reasons);
    - the wiring: only the USB cable;
    - how to flash the shadow sketch with arduino-cli, as `docs/control/device-test.md` shows for the replay;
    - the configuration file, field by field, with the example;
    - how to run the bridge and where its files go;
    - the columns of `decisions.csv` and `inputs.csv`;
    - how to read a night: the reasons over time, and the rooms' report cadence from `inputs.csv`;
    - the protocol as the table above.
    
    `docs/control/decisions.md` records that the bridge forwards retained messages, and why.
