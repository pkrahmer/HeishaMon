# The router

## Description

The router turns the core's demand into the commands for HeishaMon's optional PCB emulation, as `docs/control/firmware-design.md` §4 describes: `SetExternalThermostat1State` 2 for heating, 1 for cooling, 0 for no demand, and `SetHeatCoolMode` for the direction, whose polarity is a setting because nobody knows it yet. It sends only when the wanted state changes, never more often than `min_change_interval_s`, and checks that the command landed: the glue reports the thermostat state the pump shows, and a command that has not landed after `retry_interval_s` is sent again, up to `max_retries` times, after which the router reports a fault until the state lands or the demand changes. At start it wants no demand.

The router is pure: it takes the demand, the confirmation and an instant, and it returns the commands to send in a small struct. It sends nothing itself.

## Interface

New files: `HeishaMon/src/control/route/ctl_router.h`, `ctl_router.c`. Test file: `tests/control/test_router.c`. It uses the core's `ctl_demand`.

```c
#define CTL_ROUTER_COMMANDS_MAX 2
#define CTL_ROUTER_NAME_MAX 32
#define CTL_ROUTER_VALUE_MAX 4

typedef struct {
    double min_change_interval_s; /* default 300.0 */
    double retry_interval_s;      /* default 120.0 */
    int max_retries;              /* default 3 */
    int heat_cool_heat_value;     /* -1 unset (default), else 0 or 1: SetHeatCoolMode's value for heat */
} ctl_router_config;

typedef enum { CTL_ROUTER_IDLE, CTL_ROUTER_WAITING, CTL_ROUTER_FAULT } ctl_router_status;

typedef struct {
    int wanted_state;        /* 0, 1 or 2: the thermostat state the demand asks for */
    int sent_state;          /* -1 until the first send */
    bool has_sent;
    double sent_at;          /* instant of the last send, first or repeat */
    double changed_at;       /* instant of the last send of a new state */
    int retries;             /* repeats of the current state so far */
    ctl_router_status status;
} ctl_router;

typedef struct {
    char name[CTL_ROUTER_NAME_MAX];
    char value[CTL_ROUTER_VALUE_MAX];
} ctl_command;

typedef struct {
    size_t count;
    ctl_command command[CTL_ROUTER_COMMANDS_MAX];
} ctl_commands;

void ctl_router_config_defaults(ctl_router_config *config);
bool ctl_router_config_valid(const ctl_router_config *config);
void ctl_router_init(ctl_router *router);
int ctl_router_state_for(ctl_demand demand);
void ctl_router_step(ctl_router *router, const ctl_router_config *config, ctl_demand demand,
                     bool state_known, int reported_state, double now, ctl_commands *commands);
```

The configuration:

- The defaults are 300.0, 120.0, 3 and -1.
- `ctl_router_config_valid` is true when both intervals are finite and 0 or greater, `max_retries` is from 0 to 10, and `heat_cool_heat_value` is -1, 0 or 1.

The mapping:

- `ctl_router_state_for` gives 2 for `HEATING`, 1 for `COOLING`, and 0 for `NONE` and for every value that is no member of the enum.

`ctl_router_init`: wanted state 0, nothing sent (`sent_state` -1), retries 0, status `IDLE`.

`ctl_router_step` sets `commands->count` to 0 and then, in this order:

1. **A `now` that is not finite** changes nothing and sends nothing.
2. **The wanted state** becomes `ctl_router_state_for(demand)`.
3. **The state has landed** when `state_known` is true and `reported_state` equals `sent_state`. Then `retries` becomes 0 and the status `IDLE`, unless the wanted state differs from the sent one.
4. **A new state.** When the wanted state differs from `sent_state`, or nothing has been sent yet, the router sends it if nothing has been sent yet or `now - changed_at >= min_change_interval_s`. Otherwise it sends nothing in this step and the status stays as it is.
   - Sending writes `SetExternalThermostat1State` with the state as a decimal digit.
   - When the new state is 2 or 1 and `heat_cool_heat_value` is not -1, it also writes `SetHeatCoolMode`: `heat_cool_heat_value` for 2, its opposite (`1 - heat_cool_heat_value`) for 1. A state of 0 never sends `SetHeatCoolMode`.
   - Then `sent_state` is the new state, `sent_at` and `changed_at` are `now`, `retries` is 0, and the status is `WAITING`.
5. **A repeat.** Otherwise, when the status is `WAITING` and the state has not landed, and `now - sent_at >= retry_interval_s`:
   - while `retries` is below `max_retries`, the router writes the same commands as the send of step 4, `retries` grows by 1 and `sent_at` becomes `now`;
   - when `retries` has reached `max_retries`, the status becomes `FAULT` and nothing is sent.
6. **A fault** stays until the state lands (step 3) or a new state is sent (step 4). A fault sends nothing by itself.

## Acceptance criteria

1. The configuration, as rows of one table test:
   - the defaults are 300.0, 120.0, 3 and -1, and valid;
   - refused: a negative interval of either kind, a NaN interval, `max_retries` -1 and 11, and `heat_cool_heat_value` 2;
   - accepted: both intervals 0.0, `max_retries` 0 and 10, and `heat_cool_heat_value` 0 and 1.
2. `ctl_router_state_for`, as rows of one table test: `HEATING` gives 2, `COOLING` 1, `NONE` 0, and `(ctl_demand)7` 0.
3. The first step sends at once: on a fresh router at `now` 0.0 with `NONE`, the commands are exactly `SetExternalThermostat1State` `0`, and the status is `WAITING`.
4. Landing and send on change only: after criterion 3, a step at 10.0 with `NONE`, the state known and reported 0 sends nothing and sets the status to `IDLE`. Then a step at 20.0 with `NONE` sends nothing.
5. The heat/cool command, as rows of one table test, each from a router that has sent 0 at 0.0 and stepped at 400.0:
   - `HEATING` with `heat_cool_heat_value` -1 sends only `SetExternalThermostat1State` `2`;
   - with 1 it sends that and `SetHeatCoolMode` `1`;
   - with 0 it sends `SetHeatCoolMode` `0`;
   - `COOLING` with 1 sends `SetExternalThermostat1State` `1` and `SetHeatCoolMode` `0`;
   - with 0 it sends `SetHeatCoolMode` `1`;
   - `NONE` after `HEATING` never sends `SetHeatCoolMode`.
6. The pacing, as rows of one table test, after a send of 0 at 0.0 that has landed:
   - `HEATING` at 299.0 sends nothing and keeps the status `IDLE`;
   - `HEATING` at 300.0 sends `2`;
   - a `HEATING` at 299.0 followed by `NONE` at 350.0 sends nothing at either step, because the wanted state is the sent one again at 350.0.
7. The repeats, with the defaults, after a send of 2 at 0.0 that the pump never confirms (the state known and reported 0):
   - steps at 119.0 send nothing;
   - at 120.0 it repeats `2`, with retries 1;
   - at 239.0 nothing;
   - at 240.0 it repeats, with retries 2;
   - at 360.0 it repeats, with retries 3;
   - at 480.0 the status is `FAULT` and nothing is sent;
   - at 600.0 still `FAULT` and nothing sent.
8. Leaving the fault, as rows of one table test from the fault of criterion 7: the state known and reported 2 at 610.0 gives `IDLE` and sends nothing; or `NONE` at 610.0 sends `0` with the status `WAITING`, because 610.0 is at least 300.0 after the last change at 0.0.
9. Unknown confirmation: with `state_known` false, the router repeats and faults as in criterion 7.
10. A non-finite `now` (NaN and infinity) changes no field of the router and sends nothing.
11. `make check` stays green, and `make device` compiles with the new folder.
12. docs: `docs/control/router.md` is new. It gives:
    - the mapping as a table;
    - the polarity setting, and why it has no default;
    - the order of the six rules of a step;
    - the defaults with the reason for each, citing the EEPROM note of `docs/control/firmware-design.md` §4;
    - one worked sequence (criterion 7).
    
    `docs/control/decisions.md` records the three decisions of the feature.
