# The glue and the hook lines

## Description

This story puts the loop into the firmware. The loop, the adapters, the router, the settings and the telemetry are pure C and proven on the host; what is left is the glue that connects them to HeishaMon (`docs/control/firmware-design.md` §2.2), and six hook lines in upstream's `HeishaMon/HeishaMon.ino` that call it:

- **Settings.** At start the glue loads the settings from `/control.json` on the board's file system, or the defaults when there is no valid file.
- **Pump values.** After every decoded main data frame it reads four values of that frame, with upstream's own decoder (`getDataValue`), and hands them to the loop. The loop therefore keeps running when the broker is down (decision F-3).
- **MQTT inputs.** It subscribes to the configured room and PV topics and to its own setting topics, and hands their messages to the loop or to the settings.
- **Ticks.** On every pass of upstream's `loop()` it ticks the loop with the board's clock. After each decision it publishes the telemetry, and it sends the router's commands through upstream's `send_heatpump_command` when commands are enabled.

Commands go to the pump only when four things hold: `enabled` is 1, HeishaMon's optional PCB emulation is on, HeishaMon is not in listen-only mode, and the router has a command. Otherwise the loop still decides and publishes, and the glue logs once, on each change of that condition, why it sends nothing. The router's confirmation is the emulated frame itself: the thermostat-1 state that HeishaMon sends to the pump every second, read back from bits 2 and 3 of byte 6 of `optionalPCBQuery`, where `set_external_thermostat_1_state` writes it.

## Interface

New files: `HeishaMon/src/control/glue/ctl_firmware.h`, `ctl_firmware.cpp` (Arduino C++, compiled only by `make firmware`), and in pure C `ctl_dispatch.h`, `ctl_dispatch.c` with the test `tests/control/test_dispatch.c`.

```c
/* ctl_dispatch.h: which input a topic is, by the settings */
typedef enum { CTL_TOPIC_NONE, CTL_TOPIC_INPUT, CTL_TOPIC_SETTING } ctl_topic_kind;

typedef struct {
    ctl_topic_kind kind;
    ctl_input input;     /* CTL_TOPIC_INPUT: the input */
    size_t room;         /* CTL_TOPIC_INPUT with CTL_INPUT_ROOM: the room */
    char name[CTL_SETTINGS_NAME_MAX];  /* CTL_TOPIC_SETTING: the setting's name */
} ctl_topic;

ctl_topic ctl_dispatch_topic(const ctl_settings *settings, const char *base, const char *topic);
int ctl_dispatch_thermostat_state(uint8_t pcb_byte_6);
```

- `ctl_dispatch_topic` gives `INPUT` with `CTL_INPUT_ROOM` and its index for a topic equal to a configured room topic below `rooms`. The first equal room wins. It gives `INPUT` with `CTL_INPUT_PV` for a topic equal to a non-empty `pv_topic`.
- It gives `SETTING` with the name for `<base>/control/set/<name>`, when `<name>` is 1 to `CTL_SETTINGS_NAME_MAX - 1` characters without `/`. The setter judges the name.
- It gives `NONE` for everything else, and for an empty topic. An empty room topic matches nothing.
- `ctl_dispatch_thermostat_state` gives `(pcb_byte_6 >> 2) & 3`.

```cpp
// ctl_firmware.h
void ctl_firmware_setup(bool (*send_command)(byte *, int), void (*log_message)(char *));
void ctl_firmware_loop(PubSubClient &mqtt, const char *base, bool optional_pcb, bool listen_only);
void ctl_firmware_frame(char *data);
void ctl_firmware_subscribe(PubSubClient &mqtt, const char *base);
bool ctl_firmware_mqtt(char *topic, byte *payload, unsigned int length);
```

The glue, `ctl_firmware.cpp`:

- **Setup.** `ctl_firmware_setup` loads `/control.json`: a JSON object of names to text values, applied in file order with `ctl_settings_set`. A refused pair is logged and skipped. A missing or unreadable file, or a set that ends invalid, gives the defaults, and the reason is logged. The glue then initialises the loop with `ctl_settings_to_loop` and the clock.
- **The frame.** `ctl_firmware_frame` is called with the decoded main data frame. It reads the values of topics 14 (`Outside_Temp`), 15 (`Heat_Power_Production`), 20 (`ThreeWay_Valve_State`) and 26 (`Defrosting_State`) with `getDataValue`. It hands them to `ctl_loop_input` as `OUTDOOR`, `HEAT`, `VALVE` and `DEFROST`, at the current instant.
- **Subscriptions.** `ctl_firmware_subscribe` subscribes to every non-empty room topic below `rooms`, to a non-empty `pv_topic`, and to `<base>/control/set/+`. It then publishes every setting retained under `<base>/control/config/<name>`.
- **MQTT messages.** `ctl_firmware_mqtt` returns false, and does nothing, for a topic `ctl_dispatch_topic` gives `NONE`, so upstream handles it as before. Otherwise it returns true:
  - an input goes to `ctl_loop_input`;
  - a setting goes to `ctl_settings_set`. On `OK` the glue saves the file, applies the settings from the next tick without restarting the loop, calls `ctl_set_allowed` when `cooling` changed, and subscribes again when a topic changed. In every case it publishes the setting's current value retained under `config/<name>`, so a refused value is answered with the old one.
- **The loop pass.** `ctl_firmware_loop` reads the confirmation from the frame, passes it with `ctl_loop_confirm`, and ticks the loop at the widened `millis()` in seconds. It returns at once when no tick is due.
- **A decision.** After each decision the glue publishes the inputs, status and outputs entries of the telemetry under `<base>/control/`, not retained. When commands may go to the pump, it sends each of the record's commands with `send_heatpump_command(name, value, send_command, log_message, optional_pcb)`.
- **Never blocking.** The glue never waits and never retries a publish within one call. Its state is static, and it allocates no memory after setup.

The hook lines in `HeishaMon/HeishaMon.ino`, by the owner's leave, and no other change to an upstream file:

1. `#include "src/control/glue/ctl_firmware.h"` beside the other includes of `src/`;
2. in `setup()`, after the settings and the file system are ready: `ctl_firmware_setup(send_command, log_message);`
3. in `loop()`, after `mqtt_client.loop();`: `ctl_firmware_loop(mqtt_client, heishamonSettings.mqtt_topic_base, heishamonSettings.optionalPCB, heishamonSettings.listenonly);`
4. in `readHeatpump()`, right after the `decode_heatpump_data(data, ...)` of a main data block: `ctl_firmware_frame(data);`
5. in `mqtt_reconnect()`, after upstream's subscriptions: `ctl_firmware_subscribe(mqtt_client, heishamonSettings.mqtt_topic_base);`
6. at the very start of `mqtt_callback()`: `if (ctl_firmware_mqtt(topic, payload, length)) return;`

Each hook line ends with the comment `// control loop hook`, so that `grep -c "control loop hook" HeishaMon/HeishaMon.ino` counts them.
